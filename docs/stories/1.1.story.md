## Dev Notes

**Previous Story Insights**: No previous story - this is the foundation story.

**Project Structure**: [Source: architecture/unified-project-structure.md]
- Backend service should be created in `/backend` directory within existing repository
- Use standard Go project layout with `cmd/server/main.go` as entry point
- Internal packages in `internal/` directory: handlers, services, repositories, models, middleware, config
- Scripts in `scripts/` directory for database setup
- Maintain existing Next.js structure in `/app`, `/lib`, `/styles`

**Tech Stack Requirements**: [Source: architecture/tech-stack.md]
- Go 1.21+ as backend language
- Gin 1.9+ as HTTP web framework for REST API
- MySQL 8.0+ database with `go-sql-driver/mysql` v1.7+ driver
- JWT authentication using Go-JWT v4
- Environment management with `godotenv` v1.4+
- CORS handling with Gin CORS v1.4+
- Standard Go testing framework for backend tests

**Database Schema**: [Source: architecture/database-schema.md]
Complete schema includes 5 tables with proper relationships:
- `users` table: id, username, email, password_hash, timestamps with unique constraints
- `rooms` table: id, name, access_token (UUID), creator_id, is_active, timestamps
- `channels` table: id, name, room_id, is_main_lobby, livekit_room_name, timestamps
- `room_members` junction table: id, user_id, room_id, joined_at, is_active
- `user_channels` tracking table: id, user_id, channel_id, connected_at, livekit_participant_id
All tables use InnoDB engine with UTF8MB4 charset and proper foreign key constraints

**Backend Architecture**: [Source: architecture/backend-architecture.md]
Service architecture follows clean architecture patterns:
- `cmd/server/main.go`: Application entry point with Gin router setup
- `internal/handlers/`: HTTP request handlers (auth.go, rooms.go, channels.go)
- `internal/services/`: Business logic layer (auth_service.go, room_service.go, channel_service.go, livekit_service.go)
- `internal/repositories/`: Data access layer (user_repo.go, room_repo.go, channel_repo.go)
- `internal/models/`: Data models matching database schema
- `internal/middleware/`: HTTP middleware including authentication
- `internal/config/`: Configuration management

**Data Models**: [Source: architecture/data-models.md]
Go structs should match the database schema:
- User model with ID, Username, Email, PasswordHash, CreatedAt, UpdatedAt fields
- Room model with ID, Name, AccessToken, CreatorID, IsActive, CreatedAt fields
- Channel model with ID, Name, RoomID, IsMainLobby, LiveKitRoomName, CreatedAt fields
- Junction models for RoomMember and UserChannel relationships

**Environment Configuration**:
Backend `.env.example` should include:
- `DATABASE_URL` or separate DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD
- `JWT_SECRET` for token signing
- `SERVER_PORT` (default: 8080)
- `GIN_MODE` (debug/release)

**REST API Specification**: [Source: architecture/rest-api-spec.md]
- Health check endpoint should follow OpenAPI 3.0 spec format
- Server runs on localhost:8080 as specified in API documentation
- JWT Bearer authentication pattern defined for future endpoints
- JSON response format standards established

**Integration Requirements**:
- Backend runs on port 8080, Next.js continues on port 3000
- CORS configuration must allow localhost:3000 requests
- No interference with existing LiveKit Meet functionality
- Database operations should not impact real-time communication performance

### Testing

- Unit tests in `*_test.go` files alongside source files
- Test database connection and health endpoint functionality
- Health endpoint testing should verify OpenAPI 3.0 response format compliance
- Integration tests for database schema creation and initialization
